# Response-time baseline, 2026-10-23

The first recorded p95 baseline for the key endpoints (CLAUDE.md performance standard:
"p95 latency and queries-per-request are part of the definition of done"). Re-run it
after any change to these endpoints and add a dated file next to this one.

## Setup

- Development laptop: Intel i9-9880H (16 threads), 16 GB. API (`backend/bin/nexa serve`,
  all roles), Postgres 16 + PostGIS and Redis 7 in Docker, and the client all on one machine.
- Local data set: a handful of riders, drivers and trips (development database), so list
  endpoints are measured on small tables. Expect them to grow with data; re-measure on UAT.
- Tool: `apps/tools/measure-p95.mjs`, 200 sequential calls per endpoint after 5 warm-up
  calls, one client (latency, not throughput; throughput is in `DOC/05-capacity-plan.md`).

```
cd apps
STAFF_EMAIL=<staff email> STAFF_PASSWORD=<password> PG_CONTAINER=nexa-local-postgres-1 N=200 \
  node tools/measure-p95.mjs
```

## Results

| Endpoint | p50 ms | p95 ms | max ms | queries/req (approx) |
|---|---:|---:|---:|---:|
| GET /app/config | 0.5 | 0.7 | 1.6 | 0 |
| POST /quotes | 3.5 | 5.2 | 33.1 | 0–1 |
| GET /trips (rider) | 5.2 | 6.8 | 12.6 | 1–3 |
| GET /admin/overview | 3.2 | 4.3 | 7.9 | 0–4 |
| GET /admin/trips | 6.4 | 7.7 | 8.5 | 3–5 |
| GET /admin/riders/{id} | 7.0 | 19.1 | 56.9 | 9–15 |
| GET /admin/drivers/{id}/activity | 8.1 | 14.7 | 45.5 | 12–20 |

Every endpoint is well under the 150 ms p95 target. The queries-per-request column is
estimated from Postgres transaction counters minus the background rate of the workers
and dispatcher (8.6 transactions/s while idle), so it is noisy. The range shows three
runs (N = 50, 100, 200). It is a guide, not an exact count; `pg_stat_statements` on UAT
would give exact numbers.

## Findings

1. **`/app/config`, `/quotes` and `/admin/overview` do not touch Postgres on the hot path.**
   They are served from the in-process and Redis caches as the standard requires.
2. **`GET /admin/drivers/{id}/activity` (~12–20 queries) and `GET /admin/riders/{id}`
   (~9–15 queries) issue many queries per request.** They are still fast on a small data set,
   but the count suggests per-section lookups that should become one or two joined
   queries (no-N+1 rule). Check them with `EXPLAIN ANALYZE` on UAT data before the pilot.
3. Single-client latency hides contention. The k6 smoke below and the full 600-driver
   run on UAT (`infra/loadtest/README.md`) are the load figures.

## k6 smoke (same machine, 2026-10-23)

`infra/loadtest/platform.js` with 20 drivers pinging every 10 s and 1 quote/s for 30 s
against the development API (`docker run grafana/k6:1.3.0`). Run 1 had bookings off; in
run 2, 30 % of quotes were booked and then cancelled. No real drivers were online.

| Metric | Run 1 p95 | Run 2 p95 | Threshold | Result |
|---|---:|---:|---:|---|
| `POST /driver/location` | 15.5 ms | 8.3 ms | < 150 ms | pass |
| `POST /quotes` | 53.6 ms | 14.0 ms | < 150 ms | pass |
| `POST /trips` (book) | — | 95.7 ms | < 150 ms | pass (closest to the limit) |
| All requests | 55.8 ms (180 req) | 15.9 ms (193 req) | < 150 ms, < 1 % errors | pass, 0 % errors |

Booking is the slowest write: one transaction plus dispatch work, ~60–100 ms here. Watch it
first in the UAT run. The full run (600 drivers, 10 minutes) is for the UAT host. Running it
on this laptop would only measure the laptop.
